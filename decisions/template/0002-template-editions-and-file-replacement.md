# 2. 템플릿 판과 파일 교체 방식의 업데이트

## 상태

채택(2026-09-26).

## 배경

GitHub 의 "Use this template" 은 템플릿을 한 번 복사하고 끝납니다. 새로 만든 저장소는 템플릿의 git 이력을 이어받지 않으므로, 템플릿이 나중에 바뀌어도 고객 저장소에 그 변경을 가져올 방법이 없습니다. 템플릿을 계속 관리하려면 고객 저장소가 템플릿의 새 변경을 받아 갈 수 있어야 합니다.

## 결정

- 템플릿 저장소의 `vX.Y.Z` 태그 하나가 판 하나입니다. 발행한 판은 고치지 않고, 바꿀 때는 새 판을 냅니다.
- `template.json` 이 판의 버전과, 템플릿이 관리하는 경로(`managedPaths`)와, 관리 구역이 있는 파일(`managedBlocks`)을 정합니다. 목록에 없는 것은 저장소 주인의 것입니다.
- `swift run repo template update` 는 git 병합을 하지 않고, 관리 영역의 파일을 새 판의 파일로 교체합니다. 관리 구역이 있는 파일에서는 표시 사이의 글만 바꿉니다.
- 관리 영역에 커밋하지 않은 변경이 있으면 아무것도 쓰지 않고 멈춥니다. 업데이트 결과는 저장소 주인이 확인하고 커밋합니다.

## 검토한 대안

- **git 병합:** 기각했습니다. 고객 저장소와 템플릿 저장소의 이력이 이어지지 않으므로 첫 병합부터 모든 파일이 충돌합니다.
- **fork:** 기각했습니다. 공개 저장소의 fork 는 비공개 저장소로 만들 수 없는데, 고객의 앱 저장소는 대부분 비공개입니다.
- **copier, cruft 같은 템플릿 도구:** 기각했습니다. Python 실행 환경을 추가로 설치해야 하므로 결정 1 과 맞지 않습니다.

## 결과

- 관리 영역에 직접 고친 내용은 다음 업데이트 때 덮어써집니다. 고친 곳은 `swift run repo template update --to <현재 판> --dry-run` 으로 미리 찾을 수 있습니다.
- 업데이트는 고객 저장소에 이미 있는 옛 판의 도구가 실행합니다. 따라서 `template.json` 의 형식은 뒤로 호환되어야 하고, 업데이트 방식의 변경은 그 판을 받은 다음 업데이트부터 적용됩니다.
- 저장소 주인 영역(`repo.json`, `README.md` 등)은 새 판이 와도 바뀌지 않습니다. 따라서 새 판의 도구는 그 파일에 새 값이 없어도 동작해야 합니다.
