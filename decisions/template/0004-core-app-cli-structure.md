# 4. 앱 구조: Core, App, CLI

## 상태

채택(2026-09-26).

## 배경

이 저장소의 앱은 에이전트가 만들고 고칩니다. 에이전트는 macOS 앱의 화면을 조작하기 어렵기 때문에, GUI 만 있는 앱에서는 변경이 제대로 동작하는지 스스로 확인하기 힘듭니다. 또한 로직이 화면 코드와 섞여 있으면 로직만 따로 테스트하기 어렵습니다.

## 결정

- 앱 하나는 Swift 패키지 하나이고, 로직 라이브러리 `<Name>Core`, SwiftUI GUI `<Name>App`, CLI `<Name>CLI`, 테스트 `<Name>CoreTests` 로 나눕니다.
- GUI 와 CLI 는 Core 를 호출하기만 하고, GUI 로 할 수 있는 일은 CLI 로도 할 수 있게 만듭니다.
- GUI 실행 제품의 이름은 `<Name>App` 으로, CLI 실행 제품의 이름은 slug 로 합니다.

## 검토한 대안

- **GUI 타깃 하나에 로직까지 두기:** 기각되었습니다. 에이전트가 동작을 확인하려면 화면을 조작해야 하고, 로직 테스트가 화면 코드와 얽힙니다.
- **GUI 실행 파일이 인자를 받으면 CLI 로 동작하게 하기:** 기각되었습니다. 진입점 하나에 앱 초기화와 명령 해석이 섞이고, 명령 하나를 실행할 때도 AppKit 을 불러와야 합니다.
- **UI 자동화 테스트로 GUI 를 확인하기:** 기각되었습니다. Xcode 프로젝트와 손쉬운 사용 권한이 필요하고, SwiftPM 만으로는 돌릴 수 없으며, 실행이 느립니다.

## 결과

- 에이전트는 `apps/<slug>/.build/debug/<slug>` 로 동작을 확인하고, 데이터 디렉터리 환경 변수를 임시 디렉터리로 지정해서 실제 데이터를 건드리지 않고 시험할 수 있습니다.
- 로직 테스트가 Core 에 모이므로 `swift run repo check <slug>` 가 GUI 없이 동작을 검증합니다.
- GUI 기능을 더할 때마다 CLI 명령도 만들어야 하는 비용이 듭니다.
- 두 실행 제품의 이름이 다르므로, 한 단어 slug(예: `notes`)에서도 대소문자를 구분하지 않는 파일 시스템에서 실행 파일 이름이 충돌하지 않습니다.
